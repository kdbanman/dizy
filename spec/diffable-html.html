Diffable HTML · spec version 0.1 · normative

Diffable HTML is a constrained subset of HTML and CSS for engineering documents — rich enough for specs, PRDs, and architecture docs; constrained enough that two versions of a file can be rendered side by side, aligned block by block, with changes highlighted. This document is itself written in the subset it defines.

01 Design contract

Three guarantees buy one capability

A conformant document guarantees three things, and in exchange any two versions of it can be visually diffed:

  • Inert. No scripts, no event handlers, no forms. Nothing executes.
  • Self-contained. No external references of any kind — no images, fonts, stylesheets, imports, or media. The file renders identically offline, forever, from a single blob at a single git ref.
  • Linear. Reading order is DOM order. Styling may decorate blocks but must not relocate meaning; the document flattens faithfully to a sequence of blocks.

Inert and self-contained are what make rendering repository-controlled HTML safe at all — the reason GitHub refuses to render HTML is that arbitrary HTML is arbitrary code. Linear is what makes the side-by-side alignment model work: matched blocks pair up, spacers equalize their positions, and highlights land on the block that changed.

02 Document shape

One file, head and body

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <meta name="dizy" content="0.1">          <!-- advisory conformance declaration -->
  <title>Required</title>
  <style>/* the document's own design, under the CSS policy */</style>
</head>
<body>
  <!-- a sequence of blocks -->
</body>
</html>

The head may contain only: meta charset, meta name="viewport", meta name="description", meta name="dizy", one required title, and style elements. Everything else — link, base, script, meta http-equiv — is a violation. The dizy meta declares intended conformance; renderers validate regardless and never trust the declaration.

03 Elements

The allowlist

RoleElements
Containers (traversed, not diffed directly) main header footer nav section article aside div blockquote figure details
Leaf blocks (the units of diffing and alignment) h1–h6 p pre hr ul ol dl table figcaption summary — plus their internals: li dt dd caption thead tbody tfoot tr th td
Inline a span strong em b i s u code kbd samp var mark small sub sup abbr time del ins q cite dfn br wbr
Banned script iframe object embed img svg picture video audio canvas form input button select textarea link base template noscript, custom elements, and anything else not listed above

A container whose content is entirely inline (a styled callout div, say) is treated as a leaf block. Figures and diagrams are expressed as pre ASCII/Unicode art in 0.1 — inline SVG and data-URI images are the most likely additions in a future version, and are excluded now because each adds diff and containment questions that deserve their own decision.

05 CSS policy

Your typography, no exit

Documents carry their own design — that is the point of writing docs in HTML. The policy constrains capability, not taste:

  • At-rules: @media and @supports only, nesting allowed. @import @font-face @namespace @property @layer @keyframes @page are violations.
  • No fetch functions, anywhere: url() image() image-set() src() element() are violations in any declaration — including custom property values, which closes the --x: url(…) → var(--x) laundering route. Fonts are system stacks only.
  • No position: fixed. It escapes document flow entirely. relative, absolute, and sticky are allowed for decoration — list markers, section rules, sticky headers — under the Linear guarantee: styling must not move content out of reading order.
Enforcement vs. safety The validator enforces this policy as conformance. It is not the safety boundary. Renderers sandbox panes so that even a doc that somehow evaded validation cannot execute or fetch: an iframe with sandbox="allow-same-origin" (scripts can never run) and an injected Content-Security-Policy meta of default-src 'none'; style-src 'unsafe-inline' (no fetch can leave the pane, verified at the network level). Belt, suspenders, and the belt is spec-guaranteed.
06 The block model

How a document becomes a sequence

Renderers flatten the body depth-first: containers are entered, leaf blocks are collected. Each leaf block is fingerprinted by its tag, its whitespace-normalized text tokens, and its attribute signature. Two versions of a document then diff in three phases:

  • Exact — longest common subsequence over block fingerprints pairs the unchanged majority.
  • Fuzzy — within the gaps, blocks pair as modified when token similarity clears a threshold; equal ids force a pair; heading levels may differ (an h2 promoted to h3 is the same heading, changed).
  • Rest — unpaired old blocks are removed, unpaired new blocks are added. No move detection: a moved block reads as removed + added, on purpose.

Modified blocks get word-level highlighting (words, never characters). Tables diff by rows first — an inserted row must not smear every later row as changed. Changes to the head (title, metas, style) affect the whole page and are reported separately as a document-chrome diff rather than pretending to fit block alignment.

07 Conformance

Violations, and what happens to them

ClassExamplesConsequence
Error banned element, event handler, banned CSS construct, disallowed href scheme, missing title, disallowed head content The document is not diffable HTML. Renderers refuse the rendered view and fall back to a plain text diff, listing the violations.
Warning unknown attribute on an allowed element Stripped and reported; rendering proceeds.

Version 0.1 is deliberately strict: everything not allowed is banned, because loosening a constraint later is painless and tightening one breaks published documents. The version in meta name="dizy" exists so future renderers can apply the right policy to old files.
