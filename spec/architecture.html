dizy
Architecture · MVP shipped + full offering specified · v0.1

Dizy renders visual, aligned, side-by-side diffs of diffable HTML documents in GitHub pull requests. The MVP is a zero-backend static app; the full offering wraps the same client in a GitHub App credential layer. The invariant across both: document content never transits a Dizy server.

01 The shape

One client, an optional credential layer

Everything substantive is client-side: PR resolution, merge-base lookup, file fetching, validation, diffing, alignment, rendering. This is possible because api.github.com serves CORS to any origin, including authenticated requests. It is desirable because it makes the trust claim verifiable — open the network tab: the only host contacted is GitHub.

02 Client pipeline

Six modules, one direction

ModuleResponsibility
github.jsPR URL → merge-base SHA (three-dot semantics: /compare, never base.sha) → changed HTML files → before/after file bodies (raw media type; handles renames, forks, 1–100 MB). Tracks rate limits.
validate.jsDiffable-HTML 0.1 conformance: element/attribute allowlists, head rules, href schemes. Errors refuse the rendered view; the stripped tree is defense in depth.
cssfilter.jsCSS policy: banned at-rules, fetch functions (incl. custom-property laundering), position:fixed. Pure-string layer runs anywhere — same code will back the future CLI/CI validator.
blocks.jsBody → linear leaf-block sequence with token lists and fingerprints; stamps data-dizy-block indices that survive serialization into panes.
diff.jsThree-phase block matching (exact LCS → fuzzy Dice with id/heading keys → add/remove), word-level LCS, row-level table LCS, line diff for chrome. Pure logic, fully unit-tested.
render.js + align.jsPane srcdoc assembly (CSP meta first, base, doc styles, highlight styles), highlight application, spacer insertion, change navigation.
03 Containment

Three independent layers

  • Sandbox: panes are <iframe sandbox="allow-same-origin" srcdoc=…>. Without allow-scripts, script execution is impossible by spec — not by sanitizer diligence. Forms, popups, top-navigation, and meta-refresh are blocked by omitted flags. allow-same-origin exists so the parent can measure and mutate panes for alignment; with scripts off, it reopens nothing.
  • CSP: each pane's first head child is default-src 'none'; style-src 'unsafe-inline'. Every fetch a document could declare — img, CSS url(), @font-face, media, and vectors not invented yet — dies at the policy. Verified at the wire: a probe server sees zero requests.
  • Validation: the subset itself. What reaches a pane has already had scripts, handlers, fetching elements, and CSS fetch functions rejected. The one navigation gap sandbox leaves open (a link navigating its own frame) is closed by href rules plus a capturing click handler.
Contrast htmlpreview-class tools execute arbitrary repo content in a shared origin behind shared CORS proxies. Dizy's answer is architectural, not reputational: there is no server to trust and no execution to audit.
04 Access model

Public free, private pasted, SaaS signed

TierMechanismLimits
Anonymous (shipped)Unauthenticated api.github.comPublic repos, 60 req/hr/IP — fine for small PRs; the UI shows remaining quota
Pasted token (shipped)Fine-grained PAT (Contents:read, Pull requests:read) sent as Authorization: Bearer, held in memory only5000 req/hr, private repos. The only zero-backend private path: GitHub's OAuth token endpoints have no CORS and require a client secret even with PKCE.
GitHub App (specified)User access token via OAuth web flow; the token service (stateless edge function) holds the secret and exchanges/refreshes; the browser then calls GitHub directlyFine-grained app permissions ∩ user access ∩ installed repos; 8h tokens, 6mo refresh

An optional hardened deployment keeps tokens in HttpOnly cookies behind a proxying backend-for-frontend — trading the content-never-transits property for XSS containment. Deployment choice, default off, and the self-hosted static bundle remains the reference trust story.

05 Commenting

As the user, anchored to source

Review comments post with the user's token — GitHub attributes them to the user, no bot in the byline. The API constraint shapes the feature: comments anchor to (path, line, side) and the line must appear in the PR's three-dot diff hunks.

  • The validator gains a positional pass: it already walks the source, so it records each leaf block's source line range as it goes. Rendered block → source lines becomes a lookup, not a search.
  • Clicking a changed block offers its in-hunk lines; anything outside the hunks falls back to a file-level comment (subject_type: "file").
  • Existing review threads render beside their anchored blocks, read through the same API — review happens in the rendered view, which is the pain GitHub's own rich diff never solved.
06 Growth path

No step requires a rewrite

  • 1. MVP — static app: PR URL or local files → validated, aligned, highlighted side-by-side diff. Shipped.
  • 2. Source-line map — positional pass in the validator; pure addition.
  • 3. GitHub App + token service — "Sign in with GitHub" beside the PAT field; ~50 lines of edge function.
  • 4. Comment read/write — the review loop closes.
  • 5. Ecosystem — validator CLI and CI action from the same validate.js/cssfilter.js modules ("docs are dizy-conformant" as a status check); PR dashboards; org installs.

Open questions live on the wayfinder map: inline diff mode, subset versioning governance, embedded figures, SaaS packaging.
